# МАТРИЦА ТОВАРОВ — спека дедупа по источнику (задача #14)

> Дата: 2026-09-01. Статус: КОД ЗЕЛЁНЫЙ (модуль `ymarket_matrix_v1.py`; сухая приёмка M1–M6 — все
> прошли; norm_key: числа из name+size_hint ВМЕСТЕ, сортировка, дедуп-слов — дедуп одного товара
> из двух источников склеился, 0 дублей).
> Связано: `YM_CYCLE1_V1.md` §5, `ymarket_registry_v1.py` (канон идентификаторов), `ymarket_cats_v1.json`.

## 1. Зачем

Канон реестра хранит связь «карточка ↔ товар донора» (offerId ↔ pid/url/SKU). НЕ хранит:
чем добыт товар, из какого источника, в какой категории, на какой ступени жизни он сейчас.
Без этого добыча повторяет сама себя (тот же товар из 3 источников = 3 карточки = хаос и
риск связки). Матрица — **верхний слой добычи**: ДЕДУП по сущности товара, не по карточке.

## 2. Ключ дедупа (по убыванию силы)

1. **article** донора (pid cargo / артикул WB / SKU партнёра) — сильнейший, когда есть.
2. **EAN / barcode** — если пришёл с донором.
3. **name+размер** — нормированное наименование + габарит (0,3×100 м / 1,2×50 м). Размер ОБЯЗАТЕЛЬНО
   в ключе: «ВПП плёнка» без размера ≠ товар. Нормировка: нижний регистр, без падежей-концовок,
   цифры через «х», пробелы сжаты — как в живых уроках (см. [[ymarket-live-api-lessons]]).

Правило: **позиция, уже стоящая в «залит/на витрине/продан», в добычу не возвращается** —
по ЛЮБОМУ из трёх ключей (0 дублей формулы).

## 3. Схема записи

```
{ "schema": "ymarket.matrix.products.v1",
  "rows": { "<ключ дедупа>": {
      "key": "<ключ>",                 # нормированный дедуп-ключ
      "name": "ВПП плёнка 0,3×100 м",
      "size_hint": "0,3×100 м",
      "offer_id": "9603273-1",         # канон реестра (null до залива)
      "provider": "cargo-avto|wb|partner",   # кто добыл
      "source_url": "https://...",     # провенанс
      "category": "puzyrkovaya-plenka" # ключ ymarket_cats_v1.json
      "status": "кандидат|собран|залит|сверен|на-витрине|продан",
      "task_id": "plenerka-2026-09-01-3",   # заданиеId (директива)
      "first_seen": "...", "updated_at": "..."
  } } }
```

## 4. Законы

- **M1 не выдумываем:** без имени или ключа строка не пишется (отказ, как R1 реестра).
- **M2 дедуп строг:** новый кандидат сверяется по всем трём ключам; совпадение → апдейт
  существующей строки (добавляем источник в provider-list), НЕ новая строка.
- **M3 матрица НЕ дублирует реестр:** реестр = идентификаторы карточки (offerId↔donor),
  матрица = сущность товара + статус добычи. Никаких marketSku/shopSku тут нет.
- **M4 status лесенка:** кандидат→собран→залит→сверен→на-витрине→продан (сверен = карточка
  прошла СВЕРКУ, ступень 4 цикла — reconcile, не frozen). Откат строго вниз не
  разрешён без причины (поле `note`).
- **M5 fail-soft + атомарно:** битый файл → бланк; запись tmp+os.replace (как реестр).
- **M6 связь с заданием:** каждая строка несёт task_id → задание → категорию → партию → точку
  (паспорт `ymarket_points_v1`). Цепочка, по которой «всё что написал оператор не пропадёт».

## 5. Куда в цикл

`задание дня (планёрка) → матрица.ensure(candidates) [дедуп] → категорийщик/сборка → залив →
реестр.record → матрица.set_status(залит) → остаток → на-витрине`. Первый прогон — сухо
(0₽), приёмка M1–M6, потом живьё на cargo плёнке.
