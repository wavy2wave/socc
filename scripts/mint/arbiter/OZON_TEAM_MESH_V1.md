# ОЗОН — ПАУТИНА УЗЛОВ (OZON_TEAM_MESH_V1)

> Оргмодель ОЗОН-МЕНЕДЖЕРА как её хочет **сам Озон в идеале**: не линия ролей, а **паутина узлов**,
> где каждый узел связан с процессом, ускоряет его и **пре-питает соседа с опережением смыслов**.
> Прибыль — не отдельный узел, а **поток через паутину + петли обратной связи**.
> Статус: **КАНОН-ДИЗАЙН** (кодируется в `OZON_MANAGER_LINE_V1.json`, M0). 0₽, `live=False`, РУБИКОН в силе.

---

## 0. Принцип: паутина, а не конвейер

Конвейер ждёт: стадия N стартует, когда N−1 закончила — простой на каждом шве.
Паутина не ждёт: **каждый узел, кроме своей реактивной работы, готовит вход для следующего ЗАРАНЕЕ**
(«с опережением смыслов»). Аналитик греет следующий сезон за 6 недель до пика; индекс-сторож метит
карточку, ползущую к жёлтому, до того как она покраснела; диспетчер поднимает поставщика до того, как
упал заказ. **Опережение = ускорение.** Поток через узлы + петли обратной связи — это и есть прибыль.

Три закона паутины:
- **Связность** — у каждого узла есть вход (кто пре-питает его) и выход (кого он пре-питает). Изолированных узлов нет.
- **Опережение** — у каждого узла две работы: *реактивная* (обработать вход) и *опережающая* (подготовить выход соседу до запроса).
- **Контроль на ребре** — КОНТРОЛЁР стоит на каждом шве; «лучше ноль, чем ложь»; 200 ≠ успех.

## 1. Звенья и подкоманды (lead + узлы)

Каждое верхнее звено — не одна фигура, а **под-команда узлов**. Столбцы: реактив · **опережение** (что готовит вперёд) · живой модуль / пробел · **что за это даёт Озон**.

| **F2 ПРОДВИЖЕНЕЦ** | Реклама VCG / Premium / акции | Готовит ставки под пик A2 | пробел (опц.) | Платный ранг + участие в акциях |

### ХРЕБЕТ (сквозные узлы — на каждом ребре паутины)
- **КОНТРОЛЁР** — гейт каждого шва; недозаполненное дальше не идёт; красный индекс → снять/снизить; «лучше ноль, чем ложь».
- **ПРУФ-ЛЕТОПИСЕЦ** — `ozon_proof`: hash-chain тик-леджер, proof-gate публикации (claim→verify независимым READ витрины).
- **ПАМЯТЬ** — `ozon_state` (дневные нормы: кто залил / отгрузил / доставил) + `ozon_shift_memory` (тренд смен).
- **БРИГАДИР** — задаёт последовательный порядок смены и **раздаёт опережающие задачи** (кто что готовит вперёд).

## 2. Рёбра паутины: поток + петли (петли и делают её прибылью)

**Прямой поток (11 рабочих узлов):**
```
A1→A2→A3 → A4(бриф) → B1(охота) → B2(валидация) → B3(поставщик)
 → C1(залив) ‖ C2(контент) → C3(модерация) → D1(индекс)/D2(цена) → [КАРТОЧКА НА ВИТРИНЕ ✅]
 → заказ → E2(SLA)/E1(закупка) → E3(отгрузка) → E4(трек) → [ДОСТАВЛЕНО]
```

**Три петли обратной связи (без них паутина — просто линия):**
- **L1 · РОСТ РАНГА:** доставлено (E4) → отзыв (F1) → рейтинг → ранг ↑ → больше заказов → назад в поток.
- **L2 · УМНЕЕТ АССОРТИМЕНТ:** продажи/возвраты (ПАМЯТЬ) → АНАЛИТИК A1 → АРХИТЕКТОР A4 правит матрицу 500 SKU.
- **L3 · ИНДЕКС-ГОМЕОСТАЗ:** ИНДЕКС-СТОРОЖ D1 → РЕПРАЙСЕР D2 → зелёный индекс → видимость → продажи → индекс.

Прибыль = **пропускная способность потока × сила петель**. Узкое место (красный индекс, медленная отгрузка,
слепой ассортимент) рвёт паутину — КОНТРОЛЁР и менеджер целятся именно в узкое место (лестница решений).

## 3. «То что ОНИ хотят в идеале» — карта идеала Озона на узлы

Идеальный продавец глазами Озона = закрытые все его сигналы ранжирования. Каждый узел закрывает часть:

| Идеал Озона | Узел паутины |
|-------------|--------------|
| Продавать то, что **ищут** (поисковые запросы, «Что продавать») | A1 · A4 |
| Быть в товаре **до** пика спроса (сезон/тренд) | A2 · F2 |
| **Богатый полный** контент + rich-content | C1 · C2 |
| **Зелёный** индекс цен | D1 · D2 |
| **Быстрая** доставка FBS (2 дня > 7) | E2 · E3 |
| Высокий **рейтинг** магазина, низкий % отмен/просрочек | КОНТРОЛЁР · E-звено |
| **Отзывы** и работа с ними | F1 |
| Участие в **акциях** / реклама | F2 |

Вывод: паутина — это буквально чек-лист «идеального продавца Озон», разложенный на связанные узлы,
каждый со своей скоростью и опережением.

## 4. Доктрина продуктивности (высший уровень каждого узла)

Оператор: «прокачать каждого до самого продуктивного уровня — быстро, с опережением смыслов, понимает
новости Озона / что в кабинете». Кодируется в charter каждого узла как **три измеримых принципа**:

1. **Скорость** — у узла свой SLA-таймер (как у ДИСПЕТЧЕРА 60 мин); просрочка узла = эскалация, не тишина.
2. **Опережение** — узел обязан пре-питать соседа (столбец «Опережение» выше — это контракт, не пожелание).
3. **Знание кабинета** — узел читает изменения Озона в своей зоне (единицы измерения, ENUM-ловушки,
   новые обязательные атрибуты) и обновляет свои правила; «понимает новости» = живёт по факту кабинета, не по вчера.

Проверяется приёмкой: у каждого узла в манифесте есть `sla`, `feeds` (кого пре-питает), `reads_cabinet` (что мониторит).

## 5. Как ложится в код (M0 → далее)

- **M0 (сейчас):** `OZON_MANAGER_LINE_V1.json` кодирует паутину — узлы (lead/подкоманда), рёбра, петли,
  для каждого узла: `status` (live/gap), `module` (живой модуль или пробел), `sla`, `feeds`, `reads_cabinet`.
  + каркас `ozon_state`/`ozon_shift_memory`/`ozon_self`/`ozon_proof`/`ozon_manager` (tick, dry).
- **Живые узлы вплетаем, не пишем заново:** B1 `wb_scout`, B2 `gap/prospect/pricing`, B3 SCOUT,
  C2 `uniqueizer`, D2 `pricing`, E1 `bridge/buy_adapter`. Это и есть «мы уже делали — вернёмся».
- **Пробелы = write-плоскость** (9 эндпоинтов urllib, `live=False`) + аналитика A1 (`/v1/analytics/data`).
- **Контроль как в SOCC:** КОНТРОЛЁР на ребре, ПРУФ на тик, ПАМЯТЬ дневных норм, двойной гейт `not dry AND commit`.

*РУБИКОН: ни одной реальной карточки и ₽ без слова оператора; ключ Озона ротируется до любого write.*
