# ОЗОН-МЕНЕДЖЕР — ПЛАН ПОСТРОЕНИЯ (OZON_MANAGER_PLAN_V1)

> Орган: **МЕНЕДЖЕР ПО ОЗОНУ + команда**. Ведёт магазин к успеху «как швейцарские часы»,
> автоматизирует весь цикл, контроль на каждом стыке — как в SOCC.
> Строим ТОЛЬКО Озон. `ymarket_*` — не предмет работы, а **доказанный образец кода** (231 тест зелёный), который зеркалим.
> Статус: **ПЛАН**. Ни одной карточки, ни одного ₽ наружу без слова оператора (РУБИКОН). `live=False` по умолчанию.

---

## 0. Принцип (как в SOCC)

Менеджер — это **не демон, а TICK-цикл**. Он живёт между запусками через ПАМЯТЬ (state + shift_memory), а не через висящий процесс.
Каждый тик: `читаю память → само-статус → решаю по лестнице → исполняю (fail-soft) → пишу назад → доказываю тик (proof) → рисую`.
Это ровно паттерн `ymarket_manager_v1.tick()`, доказанный на Яндекс-стороне. Мы его зеркалим под Озон, меняя ТРИ вещи:
**транспорт (urllib)**, **payload-шейпы под Ozon Seller API**, **бизнес-константы (0.298 / ₽325)**. Всё остальное — почти дословно.

## 1. Формула успеха магазина Озон (якорь дизайна)

Не «на ощущениях» — 6 мультипликативных рычагов (веб-разведка 2026 + факт кабинета). Вся команда строится ПОД них:

| # | Рычаг | Что значит для органа | Чья зона |
|---|-------|------------------------|----------|
| 1 | **Индекс цен** | Красный/жёлтый индекс = алгоритм ПЕРЕСТАЁТ показывать карточку = де-факто невидимость. 4 уровня (Невыгодный→Умеренный→Выгодный→Супер-выгодный). | ЦЕНОВИК-ИНДЕКС |
| 2 | **Скорость доставки** | Теперь ПРЯМОЙ фактор ранжирования. 2 дня бьют 7. | СНАБЖЕНЕЦ-ДИСПЕТЧЕР + ОТГРУЗЧИК |
| 3 | **Контент карточки** | Заголовок = главный якорь матчинга. Полнота атрибутов = попадание в фильтры витрины. | ЗАЛИВЩИК-КАРТОЧНИК |
| 4 | **Реклама / платное ранжирование** | Часть финального скоринга (VCG-аукцион). Выкл = просадка и в органике. | ПРОДВИЖЕНЕЦ (опц., позже) |
| 5 | **Рейтинг / отзывы** | Множитель доверия. | КОНТРОЛЁР (мониторит) |
| 6 | **Premium** | +5–7.5% в высококонкурентных нишах. | опц. |

**Стратегический вывод (самый дешёвый путь к ₽):** ниша с низкой конкуренцией + супер-выгодный индекс + быстрая отгрузка + чистый полный контент.
Реклама/Premium — потом, по решению оператора.

≈ ₽598 нетто на продажу

Дешёвые товары хуже: ₽325 доставки съедают маржу. Отбор обязан это учитывать (уже закодировано в `prospect`/`pricing`).

## 2. Оргструктура: МЕНЕДЖЕР ОЗОН + команда

**Дословный перевод слов оператора в роли** (каждая — файл-роль, зеркало `ymarket_role_*`):

```
                     ┌─────────────────────────────────────┐
                     │           МЕНЕДЖЕР ОЗОН              │  ← ozon_manager_v1.py (tick-оркестратор)
                     │  контролирует ВСЕ процессы дохода     │
                     │  и его РОСТА. Держит дневные нормы,   │
                     │  знает: кто залил, кто отгрузил,      │
                     │  кто доставил. Ведёт магазин к успеху.│
                     └───────────────┬─────────────────────┘
                                     │ БРИГАДИР смены задаёт ПОСЛЕДОВАТЕЛЬНЫЙ порядок
     ┌───────────┬───────────┬───────┴───────┬───────────────┬───────────────┐
     ▼           ▼           ▼               ▼               ▼               ▼
 ТОВАРОВЕД   ЗАЛИВЩИК-   ЦЕНОВИК-        СНАБЖЕНЕЦ-      ОТГРУЗЧИК       КОНТРОЛЁР
 «за товары» КАРТОЧНИК   ИНДЕКС          ДИСПЕТЧЕР       «кто отгрузил»  «контроль
             «заливка из «за индекс»     «заказ→поставщик              везде»
             других сайтов»              →фоново→курьер»
```

| Роль | Дословно оператор | Ответственность | Закон роли |
|------|-------------------|-----------------|------------|
| **МЕНЕДЖЕР ОЗОН** | «приведёт магазин к успеху… контролирует все процессы дохода и его увеличение» | Оркестрация тика, дневные нормы, лестница решений, пруф каждого тика | Не демон — TICK; непрерывность через память; ведёт к РОСТу (не только к факту) |
| **ТОВАРОВЕД** | «кто-то за товары» | Отбор доказанных связок (спрос+маржа+честная цена) | Только PROVEN связки (falsifiable-тест); дешёвый товар режется доставкой |
| **ЗАЛИВЩИК-КАРТОЧНИК** | «кто-то за заливку из других сайтов» | WB→Ozon: создать карточку, ПОЛНОСТЬЮ заполнить, вывести на витрину | «Полностью заполнена И на витрине» = единственный DONE (см. §4) |
| **ЦЕНОВИК-ИНДЕКС** | «кто-то за индекс» | Цена + мониторинг индекса цен, держать «выгодный/супер-выгодный» | Красный/жёлтый индекс = карточка невидима → снизить цену или снять |
| **СНАБЖЕНЕЦ-ДИСПЕТЧЕР** | «получили заказ — быстро нашли магазин-поставщик — фоново заказали — ждём курьера» | Заказ→поставщик→фоновая закупка→трек курьера | Быстрая доставка — прямой фактор ранга; таймер SLA как у ДИСПЕТЧЕРА |
| **ОТГРУЗЧИК** | «кто как отгрузил заказы» | Этикетка FBS + отправка + подтверждение | 200≠успех; отгрузка подтверждается статусом postinga |
| **КОНТРОЛЁР** | «везде контроль как в SOCC» | Гейты, пруф-цепь, качество карточек, индекс, рейтинг | «Лучше ноль, чем ложь»; индекс<порог → отключение; не пускает недозаполненное дальше |
| *ПРОДВИЖЕНЕЦ* (опц.) | (рост) | Реклама/Premium в высококонкурентных нишах | Включается по решению оператора, после базы |

## 3. Последовательный конвейер (последовательно — как требует оператор)

Бригадир задаёт **строгий порядок смены** (зеркало `ymarket_brigade`). Стадия N не стартует, пока N−1 не прошла гейт КОНТРОЛЁРА.

| # | Стадия | Роль | Существующий модуль (переиспользуем) | Статус | Пробел записи (строим) |
|---|--------|------|--------------------------------------|--------|------------------------|
| 1 | Отбор товара | ТОВАРОВЕД | `wb_scout_v1` + `gap_v1.prove` + `socc_mint_prospect_v1` + `pricing_v1.decide_price` | **ГОТОВО** (dry-доказано) | — |
| 2 | Заливка карточки (WB→Ozon), полное заполнение | ЗАЛИВЩИК | `uniqueizer_v1` (заголовок/EAN/фото-план) | **ЧАСТИЧНО** | `/v3/product/import` + `/v1/description-category/attribute` |
| 3 | Вывод на витрину + проверка видимости | ЗАЛИВЩИК/КОНТРОЛЁР | — | **ПРОБЕЛ** | `/v1/product/import/info` + `/v1/product/info/list` (visible/moderation) + `/v2/products/stocks` |
| 4 | Цена + индекс | ЦЕНОВИК-ИНДЕКС | `pricing_v1.decide_price` (индекс, 3 пути) | **ЧАСТИЧНО** | `/v1/product/import/prices` (запись) + `/v1/product/info/prices` (читать `price_index`) |
| 5 | Приём заказа | СНАБЖЕНЕЦ | `socc_mint_ozon_v1.fetch_new_orders` (`/v3/posting/fbs/list`) + `bridge_v1.read_orders/normalize` | **ГОТОВО** (read) | — |
| 6 | Найти поставщика → фоново заказать | СНАБЖЕНЕЦ | `bridge_v1.to_buy_task` + `buy_adapter_v1.ManualTicket` (BrowserBot за флагом) | **ЧАСТИЧНО** | авто-закупка WB (BrowserBot/Playwright) — за флагом |
| 7 | Отгрузка → ждём курьера → доставка | ОТГРУЗЧИК/ДИСПЕТЧЕР | — | **ПРОБЕЛ** | `/v2/posting/fbs/package-label` + `/v2/posting/fbs/ship` + трек доставки |

Итог: **передок (отбор + приём заказа) уже доказан**, физически не хватает **write-плоскости** (создать/заполнить/вывести/цена/остаток/этикетка/отгрузка) и **авто-закупки** на стороне поставщика.

## 4. Закон жизненного цикла карточки (дословно оператора)

> «Скачали товары — они должны быть **полностью заполнены** и **уже показываться на витрине**».

Кодируем как жёсткий инвариант КОНТРОЛЁРА. Карточка проходит 4 состояния, DONE — только последнее:

```
СКАЧАНА          → есть исходник WB (sku/url/фото), уникализирована (заголовок+EAN)
ЗАЛИТА           → /v3/product/import принят, product_id получен      (ещё НЕ готова)
ПОЛНОСТЬЮ ЗАПОЛНЕНА → все ОБЯЗАТЕЛЬНЫЕ атрибуты категории проставлены   (истина: /v1/description-category/attribute)
НА ВИТРИНЕ ✅      → модерация OK  И  visible=true  И  stock>0            (единственный DONE)
```

- «Полностью» ≠ «залито»: истина обязательности — `/v1/description-category/attribute` для категории товара. Нет обязательного атрибута → КОНТРОЛЁР не пускает дальше.
- «На витрине» ≠ «создано»: подтверждается чтением `/v1/product/info/list` (статус модерации + флаг видимости) И остатком > 0.
- **200 ≠ успех**: Ozon отдаёт `200 OK` с `errors[]`/в статусе — карточка может «висеть» замороженной. КОНТРОЛЁР читает ошибки, а не HTTP-код.

## 5. Поток заказа (дословно: заказ → поставщик → фоново → курьер)

```
posting "awaiting_packaging"          ← fetch_new_orders (/v3/posting/fbs/list)  [ГОТОВО]
   → bridge.normalize_posting          → нормализованный заказ                     [ГОТОВО]
   → найти магазин-поставщика (WB)      → адаптер поставщика (SCOUT/bridge)         [ЧАСТИЧНО]
   → ФОНОВО заказать у поставщика       → ManualTicket (сейчас) / BrowserBot (флаг) [ЧАСТИЧНО]
   → ждём курьера                        → трек статуса закупки                     [ПРОБЕЛ трек]
   → этикетка + отгрузка FBS            → package-label + ship                      [ПРОБЕЛ write]
   → settle в LEDGER                     → verified ₽ (RUBICON)                     [ГОТОВО econ]
```
SLA-таймер (быстрая отгрузка = рычаг №2) — зеркало `ymarket_role_dispatcher` (таймер 60 мин).

## 7. Контроль везде — как в SOCC

1. **Двойной гейт** — `not dry AND commit` → сеть. По умолчанию dry.
2. **Пруф-цепь на каждый тик** — `ozon_proof.emit_tick_proof` (зеркало `ymarket_proof`): пруф-стадии publish=claimed / verify=verified (карточка без верификации видимости — только *заявлена*, не *доказана*).
3. **200 ≠ успех** — читаем `errors[]`/`warnings[]`, а не HTTP-код.
4. **Само-статус** — `ozon_self.self_status`: орган знает своё состояние до действия.
5. **Лестница решений менеджера** (зеркало tick-ladder):
   `cards_errored>0 → AWAIT_FIX` · `need_mapping>0 → AWAIT_MAPPING` · `cards_tracked==0 → AWAIT_PREFLIGHT` · `ready_to_publish>0 → AWAIT_FIRST_PUBLISH (РУБИКОН)` · `index_red>0 → FIX_INDEX` · `avg_rating<TOP → TRACK` · иначе `HOLD`.
6. **Дневные нормы** — в `ozon_state`/`ozon_shift_memory` + tick-ledger: сколько залито / отгружено / доставлено за день; менеджер знает «кто как» по каждому postinga.
7. **КОНТРОЛЁР** — жёсткие красные линии: карточка не «на витрине» → не в норму дня; индекс красный → снять/снизить; «лучше ноль, чем ложь».
8. **fail-soft** — любая роль падает мягко, конвейер жив, честный REJECTED вместо тихого вранья.

## 10. РУБИКОН и дисциплина (безопасность — в силе)

- `live=False` по умолчанию + двойной гейт (`not dry AND commit`). Ничего наружу без явного слова.
- **Ключ Ozon скомпрометирован** (прошёл через чат) → **РОТАЦИЯ в кабинете (Настройки→API) до любого write**. Ключ никогда не в коде/гите/эхо.
- Не ломать что работает: правки общих файлов только обратносовместимо + **перепрогон M1 приёмок ARBITER (11/11 или 12/12) после**.
- Сухую read/write-плоскость строим ЦЕЛИКОМ до записи наружу.
- На реальных развилках — спрашиваем оператора, не угадываем.
