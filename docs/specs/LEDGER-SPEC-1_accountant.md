## 0. Зачем LEDGER и какой страх он убивает

LEDGER убивает страх **«я не контролирую».** Он превращает всё, что делает команда, в **числа, которые
нельзя подделать**, потому что каждое — из реального залогированного события. Это твой дашборд истины.

Глубже: LEDGER — это **фитнес-сенсор организма**. Эволюция (TFS-1 §6: «всё живое стремится стать лучше»)
работает только если есть чем мерить «лучше». Нет измерения → нет отбора → нет эволюции. LEDGER — тот орган,
который даёт системе **давление отбора**: паттерн промотируется в геном (PXS-1 §9) лишь когда LEDGER
**замерил** прирост. Без него «само-улучшение» — лозунг; с ним — контур.

И он же делает правдой обещание B0: *«ни один пациент не теряется — и ты видишь это в числах».* Числа — это LEDGER.

### 0.5 На пальцах (такт УЧУ — два термина, на которых стоит весь proof)

> **Атрибуция** — честный ответ на вопрос *«эту запись поймала ИМЕННО ANNA?»*. Не всякая бронь — заслуга
> ANNA; засчитываем только ту, что **была бы потеряна без неё** (пациент написал ночью, живой админ бы не
> ответил). Зачем: proof-кейс должен пережить скепсис владельца, а не рассыпаться от первого «ну это и так бы записались».
>
> **Консервативный счёт** — правило *«сомневаешься — НЕ засчитывай»*. Лучше показать ₽80k, которые железно
> твои, чем ₽200k, в которых половина спорная. Зачем: **недосчёт побеждает.** Заниженное число, которое
> владелец не может опровергнуть, продаёт сильнее, чем красивое, но дырявое. Честность здесь = оружие.

## 1. LEDGER как роль `R_LEDGER` (шаблон TFS-1 §1.1)

| поле | значение |
|---|---|
| `id` | `LEDGER` |
| `mandate` | мерить proof по каждой клинике: заявок поймано · ₽ возвращено · ROI · retention · токен-экономика |
| `responsibilities` | инструментовка событий · захват · **атрибуция** · расчёт ROI · retention · стоимость/маржа · выпуск proof-числа |
| `Σ` | `instrument(events)` · `capture(event)` · `attribute(booking)` · `compute_roi(D.pricing)` · `track_retention` · `account_tokens` · `emit_proof_number` |
| `Λ` | §4 — **нет числа без залогированного события; атрибуция консервативна; стоимость считается, не только доход** |
| `f` | точность прогноза ₽-возврата vs факт (TFS-1 §6) — LEDGER честен даже к себе |
| `Φ` | §3 |
| `deps` | вход: события от `SCOUT/HERMES/ANNA/FORGE/WARDEN` · выход: `SCRIBE`(числа для ROI/proof-кейса), эволюционный гейт, дашборд оператора |

LEDGER доменно-инвариантен: метрика потери приходит из `D.pricing` (стоматология — пропущенная заявка ×
средний чек; барбершоп — пропущенная запись × тикет). Форма счёта одна.

## 2. Под-DAG LEDGER `G_ledger` (атомы, PXS-1 §1.4)

```
 l0 instrument ──▶ l1 capture ──▶ l2 attribute ──▶ l3 roi ──▶ l6 emit_proof_number ──▶ SCRIBE c5 / B3
                       │                              ▲
                       ├──▶ l4 retention             │
                       └──▶ l5 token_economy ────────┘ (стоимость в знаменатель ROI)
```

| атом | action | вход (`pre`) | эффект |
|---|---|---|---|
| `l0` instrument | `instrument` | список событий-источников | определены события: пойман-ночной-контакт, бронь, отказ, оплата |
| `l1` capture | `capture` | `l0` PASS ∧ живые события | реальный лог событий (append-only) |
| `l2` attribute | `attribute` | `l1` PASS | каждая бронь помечена: ANNA-attributable? (консервативно) |
| `l3` roi | `compute_roi` | `l2`+`l5` PASS ∧ `D.pricing` | ₽ возвращено = attributable × чек; ROI = возврат / стоимость |
| `l4` retention | `track_retention` | `l1` PASS | клиника жива/продлевает — ранний сигнал оттока |
| `l5` token_economy | `account_tokens` | `l1` PASS | стоимость на клинику, маржа (честный знаменатель) |
| `l6` emit_proof_number | `emit_proof_number` | `l3` PASS | proof-число: «ANNA поймала N = ₽X, ROI Z×» → открывает `SCRIBE.c5`, узел `B3` |

`l6` PASS — это патрон proof-кейса. Без него `B3` (главный патрон доктрины) недостижим.

## 3. Предикаты `Φ` (реальные, PXS-1 §1.3)

```
Φ(l1):  { json_true: append_only,                       # лог нельзя переписать задним числом
          json_true: every_entry_timestamped }
Φ(l2):  { json_true: each_booking_has_attribution,      # у каждой брони есть вердикт «ANNA или нет»
          json_true: attribution_conservative }         # спорное → НЕ ANNA (LG2)
Φ(l3):  { json_true: cost_in_denominator,               # ROI считает стоимость, не только доход (LG4)
          json_true: every_number_traces_to_event }     # нет числа без события из l1
Φ(l6):  { proof_pass: roi_proof,                         # выпускается только на PASS l3
          json_true: undercount_not_overclaim }         # число занижено-консервативно
```

Инвариант честности: число без события из лога `l1` = FAIL. LEDGER **не умеет выдумывать метрику** —
он умеет только читать то, что реально произошло. Это `Λ₀ no_revenue_claim`, доведённый до механизма.

## 4. Закон LEDGER `Λ_LEDGER` (почему числам можно верить)

Усиливает `Λ₀`:
- **LG1 — событийность.** Любое число привязано к записи в append-only логе `l1`. Нет события — нет числа.
- **LG2 — консервативная атрибуция.** Бронь засчитывается ANNA только если она **правдоподобно была бы
  потеряна** без неё. Сомнение → не засчитывать. Недосчёт, не переоценка.
- **LG3 — без заявления сверх леджера.** Никакого ROI/дохода «на глаз». Только то, что выпустил `l6`.
- **LG4 — честный знаменатель.** ROI считает стоимость (токены, инфра, онбординг), а не только доход.
  Маржа реальна, не приукрашена.

> Почему это даёт контроль, а не отнимает: дашборд, где каждое число можно ткнуть и дойти до события, —
> это и есть контроль. Ты не «веришь отчёту» — ты можешь **проверить** любую цифру до её причины.

## 5. LEDGER как двигатель эволюции (стыковка TFS-1 §6 + PXS-1 §9)

```
для каждой роли Rᵢ:  fᵢ ← LEDGER.measure(события Rᵢ)        # реальный замер, не оценка
эволюционный гейт φ_promote (PXS-1 §9) ПРОПУСКАЕТ паттерн ⟺ LEDGER подтвердил прирост fᵢ ≥ θ на ≥ k доменах
```

Так LEDGER — **давление отбора** всего организма: выживают только паттерны, реально поднявшие число.
Это превращает «команда умнеет» из лозунга в измеримый монотонный процесс. Конкурентов обгоняем не рывком,
а суммой замеренных приростов, каждый из которых прошёл через LEDGER.

## 7. Тест приёмки LEDGER (фальсифицируемый)

```
(LD1 event-backed)   число без события в логе l1 → l3/l6 = FAIL.                       [LG1]
(LD2 conservative)   спорная бронь засчитана как ANNA → l2 = FAIL (должна быть «не ANNA»). [LG2]
(LD3 honest-roi)     ROI без стоимости в знаменателе → l3 = FAIL.                        [LG4]
(LD4 unblock)        l6 PASS ⟹ SCRIBE.c5 (proof-кейс) и узел B3 получают реальное число. [§2]
(LD5 fitness)        LEDGER.measure(Rᵢ) даёт fᵢ, на котором гейт PXS-1 §9 принимает/режет паттерн.
```

## 8. Граница честности (что LEDGER НЕ делает)
- Не привлекает, не онбордит, не говорит с пациентом — только **мерит** то, что сделали другие.
- Не обещает будущий доход — мерит **случившийся** возврат (прогноз `f` — отдельно и проверяется фактом).
- Намеренно **занижает**, а не завышает (LG2): proof должен пережить скепсис.
- DAG-исполнение `G_ledger` — DESIGN до §7; гейт под ним (`run_step`) доказан (PXS-1 §12).

---

> **Место в карте.** LEDGER — глаза и совесть машины: делает обещание B0 («видишь в числах») правдой,
> собирает патрон proof-кейса B3, и даёт давление отбора, без которого эволюция (TFS-1 §6) невозможна.
> Числа — это главный патрон. LEDGER их и чеканит.
