## 0. Зачем HERMES и какой страх он убивает

Твой самый большой страх — «я не умею продавать, боюсь общения». HERMES существует, чтобы **этот страх
делегировать сущности.** Он пишет, ты только подтверждаешь «отправить». Со временем, когда шаблоны докажут
себя числами, даже «отправить» уходит в автономию — но никогда раньше, чем заслужено (§4).

> **Превращение страха в кнопку.** «Страх разговора» → «нажать approve». HERMES не уговаривает — он
> показывает владельцу **его собственную потерю** и готовое решение в одном касании. Возражать нечему —
> человек сам видит дыру в своих деньгах.

### 0.5 На пальцах (такт УЧУ — два термина)

> **Follow-up sequence (секвенция касаний)** — не одно сообщение, а заранее заданная цепочка: 1-е касание →
> если молчит, через N дней мягкое напоминание → ещё одно с новым углом. Зачем: 80% ответов приходят не на
> первое касание. Машина не забывает и не передавливает — цепочка задана и лимитирована.
>
> **Objection-bank (банк возражений)** — заготовленные честные ответы на типовые «дорого / у нас есть
> администратор / боюсь роботов». Зачем: ты никогда не «зависнешь, не зная что ответить» — ответ уже
> откован SCRIBE и проверен на честность (без обещаний, которых продукт не держит).

## 1. HERMES как роль `R_HERMES` (шаблон TFS-1 §1.1)

| поле | значение |
|---|---|
| `id` | `HERMES` |
| `mandate` | превращать цели с доказанной болью в заинтересованных владельцев |
| `responsibilities` | персональное касание · выбор канала · секвенция · ответы по objection-bank · бронь/ссылка demo |
| `Σ` (грамматика) | `draft(target, evidence, positioning)` · `pick_channel(D.channels)` · `send(channel,msg)` *[approve-gated]* · `sequence(followups)` · `answer(objection)` · `handoff_demo()` |
| `Λ` (закон роли) | §4 — анти-спам, лимиты, ToS канала, **нет send без approve** (пока не заслужено), без ложных обещаний |
| `f` (фитнес) | `reply-rate · demo-rate` на касание; **штраф за жалобы/спам** (TFS-1 §6) |
| `Φ` (предикаты) | §3 |
| `deps` | вход: `SCOUT`(список+боль), `SCRIBE`(позиционирование, objection-bank), `ANNA`(demo-ссылка) · выход: `LEDGER`(метрики) |

HERMES доменно-инвариантен: канал и закон анти-спама приходят из `D.channels` / `D.law_overrides`.
Крючок, выученный на стоматологии, через геном `G_HERMES` доступен барбершопу (TFS-1 F2).

## 2. Под-DAG HERMES `G_hermes` (атомы, PXS-1 §1.4)

```
 h0 ingest ──▶ h1 draft ──▶ h2 APPROVE ──▶ h3 send ──▶ h4 sequence ──▶ h5 answer ──▶ h6 handoff_demo ──▶ LEDGER
   (SCOUT list)   ▲              ▲(человек)                                  ▲
                  │              │                                          │
            SCRIBE positioning   ты: «отправить»                     SCRIBE objection-bank
```

| атом | action | вход (`pre`) | эффект |
|---|---|---|---|
| `h0` ingest | — | `SCOUT_LIST_PROOF` PASS (PXS-1 §8) | принят ранжированный список с доказательствами боли |
| `h1` draft | `draft` | `h0` PASS ∧ `POSITIONING_PROOF` PASS | персональное касание на доказательстве боли цели |
| `h2` approve | — (человек) | `h1` PASS | оператор подтвердил конкретный текст/получателя |
| `h3` send | `send` | `h2` PASS ∧ `legal_guard` | касание отправлено в `D.channel` |
| `h4` sequence | `sequence` | `h3` PASS ∧ нет ответа N дней | следующее касание из цепочки (лимитировано) |
| `h5` answer | `answer` | пришло возражение | честный ответ из objection-bank |
| `h6` handoff_demo | `handoff_demo` | интерес подтверждён | дана demo-ссылка ANNA / забронировано демо |

`h6` PASS → метрика в LEDGER (ответы, демо — реальные числа = боеприпас proof-кейса).

## 3. Предикаты `Φ` — что даёт PASS (реальные, PXS-1 §1.3)

```
Φ(h1):  { json_true: touch_references_real_evidence,   # касание ссылается на КОНКРЕТНОЕ доказательство боли цели
          json_true: no_unproven_claims }              # в тексте нет обещаний, которых продукт не держит (Λ₀)
Φ(h2):  { json_true: operator_approved }               # есть запись approve именно этого касания
Φ(h3):  { json_true: within_rate_limit,                # §4 лимит канала не превышен
          json_true: channel_tos_ok }
Φ(h4):  { json_eq: followup_count ≤ D.max_followups }  # секвенция не переходит в спам
Φ(h6):  { json_true: positive_intent_logged }          # демо отдаётся только при подтверждённом интересе
```

Инвариант честности: `h1` без ссылки на **реальное** доказательство боли = FAIL. HERMES не может написать
«в пустоту» или приукрасить — текст обязан опираться на то, что SCOUT доказал. Касание = показанная потеря.

## 4. Закон HERMES `Λ_HERMES` — approve-gate и анти-спам (твой «законно, репутация цела»)

Усиливает `Λ₀` (PXS-1 §5):

- **H1 — нет send без approve.** Пока шаблон не доказал себя, `h3` требует `operator_approved=True`. Без него
  атом FAIL, ничего не уходит. Автономия **зарабатывается**: только после серии PASS с хорошим `f` и нулём
  жалоб конкретный шаблон может получить ослабление approve — отдельным доказанным гейтом, не оптом.
- **H2 — лимиты и ToS.** Частота/объём касаний ограничены правилами канала; превышение = FAIL `h3` (fail-closed).
- **H3 — честность касания.** Никаких ложных обещаний, поддельной срочности, выдуманной потери. Потеря,
  которую показывает HERMES, — это **доказательство SCOUT** (скрин/ссылка), не выдумка.
- **H4 — стоп по сигналу.** «Не пишите мне» → секвенция этой цели немедленно закрыта; повтор запрещён.

> Почему это защищает тебя: approve и лимиты — не тормоз, а **щит репутации**. Машина делает 90% (находит,
> пишет, ведёт цепочку, отвечает), ты делаешь 10% (жмёшь approve), доля ручного падает по мере доказанной
> безопасности. Это честная автономия, не «магия сама всё разослала».

## 5. Killer-механизм касания (из твоей задумки, дословно)

```
SCOUT доказал: клиника не ответила в директ в 22:47 (скрин приложен).
HERMES(h1) черновик владельцу:
  «Написал вам как пациент вчера в 22:47 — ответа не было до утра. Этот пациент ушёл к соседям, вот скрин.
   ANNA ответила бы за 4 секунды и записала бы его. Вот она — напишите ей сами: [demo].»
ты(h2): approve →  HERMES(h3): отправил →  владелец сам идёт в demo →  ANNA доказывает себя.
```

Это не продажа. Это **показанная потеря + готовое решение** в одном касании, на реальном доказательстве.
Тебе не нужно уметь продавать — нужно нажать approve.

## 6. Рождение, фитнес, эволюция

- `Π(R_HERMES, D)` (TFS-1 §2): bind `send`→коннектор `D.channels`, attach `Λ_HERMES ⊕ D.law_overrides`,
  mount objection-bank и позиционирование из SCRIBE, register `entity_substrate/entities/<D>/hermes/` + proof.
- `f_HERMES = reply-rate · demo-rate − штраф(жалобы/спам)` — считает LEDGER реально.
- Эволюция (PXS-1 §9): крючок/формулировка, поднявшая `reply-rate` ≥ θ на ≥ k доменах, промотируется
  `K_HERMES → G_HERMES` обезличенно. Лучший крючок становится общим достоянием всех продуктов.

## 7. Тест приёмки HERMES (фальсифицируемый)

```
(HM1 no-send-without-approve) operator_approved=False → h3 = FAIL, сообщение НЕ ушло.          [H1]
(HM2 evidence-bound)          draft без ссылки на доказательство боли → h1 = FAIL.             [Φ(h1)]
(HM3 anti-spam)               followup_count > D.max_followups → h4 = FAIL, цепочка стоп.      [H2/H4]
(HM4 handoff)                 h6 PASS ⟹ demo-ссылка отдана только при positive_intent_logged. [Φ(h6)]
```

Красные тесты = HERMES заявлен, не доказан. Зелёные = «машина пишет, ты жмёшь approve» становится proof.

## 8. Граница честности (что HERMES НЕ делает)

- Не рассылает без approve, пока автономия не заслужена конкретным шаблоном (H1).
- Не обещает того, чего ANNA/продукт не держит (H3, `Λ₀ no_*_claim`).
- Не ищет цели сам — это SCOUT; не онбордит — это FORGE. HERMES только **привлекает**.
- DAG-исполнение `G_hermes` — DESIGN до §7; гейт под ним (`run_step`) уже доказан (PXS-1 §12).

---

> **Место в карте.** SCOUT находит и доказывает боль → **HERMES** превращает её в интерес (ты только approve)
> → ANNA в demo закрывает → FORGE онбордит → LEDGER считает чек. HERMES — звено, где исчезает страх продаж:
> не ты продаёшь, а доказанная потеря говорит сама.
