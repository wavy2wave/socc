## 0. Зачем именно SCOUT первым

SCOUT — это твоё дословное «под капотом ищет клиник, вечно, неубиваемо». Он выбран первым атомом
операционного слоя, потому что:

- **не ждёт ANNA.** Охота за клиниками не зависит от готовности мозга — растёт параллельно (ветка B).
- **наполняет воронку до залпа.** Пока строится продукт, копится список целей с доказанной болью.
- **первый честный инстанс TFS-1.** Если SCOUT родится по шаблону роли и пройдёт гейты PXS-1 — функтор
  перестаёт быть теорией на одном живом примере.

### 0.5 На пальцах (такт УЧУ — два термина, на твоём кейсе)

> **ICP (Ideal Customer Profile)** — портрет клиники, которой ты максимально полезен. Не «любая
> стоматология», а например: *частная, 2–6 кресел, есть Instagram/2ГИС, ведёт запись вручную или медленно
> отвечает*. Зачем: чтобы охотник не тратил выстрелы на тех, кому ты не нужен.
>
> **Pain-signal (сигнал боли)** — видимый снаружи факт, что клиника теряет деньги на том, что чинит ANNA.
> Пример: *не ответили в директ за ночь · нет онлайн-записи · отзыв «не дозвониться»*. Зачем: касание
> HERMES строится на **показанной потере**, а не на уговорах. Нет сигнала боли — нет честного касания.

SCOUT существует, чтобы превращать «весь рынок» в «ранжированный список клиник, у каждой — доказанная боль».

## 1. SCOUT как роль `R_SCOUT` (по шаблону TFS-1 §1.1)

```
R_SCOUT = ⟨ id, mandate, responsibilities, Σ, Λ, f, Φ, deps ⟩
```

| поле | значение |
|---|---|
| `id` | `SCOUT` |
| `mandate` | наполнять воронку клиниками с ICP-фитом и **видимой** болью |
| `responsibilities` | источники · извлечение · детект боли · скоринг · ранжирование · доказательство |
| `Σ` (грамматика) | `survey(source)` · `extract(raw)→targets` · `detect_pain(target, D.icp_signals)` · `score(target)` · `rank(set)` · `emit_evidence(target)` |
| `Λ` (закон роли) | §4 — легальность сбора, лимиты, без хранения лишних ПДн, без касаний (это не SCOUT) |
| `f` (фитнес) | `precision = |целей с подтверждённой болью| / |всего в списке|` (считает LEDGER, реально) |
| `Φ` (предикаты) | §3 — проверки, по которым атомы SCOUT получают PASS |
| `deps` | вход: `SCRIBE`(ICP-критерии) · выход: `HERMES`(касание), `LEDGER`(метрики) |

> SCOUT **доменно-инвариантен по форме.** Стоматология и барбершоп используют *одного и того же* SCOUT;
> различие приходит из домена `D` (TFS-1 §3): `D.sources[]`, `D.icp_signals[]`, `D.vocabulary[]`.
> Улучшил детектор боли один раз → выиграли все продукты (TFS-1 F2).

## 2. Под-DAG SCOUT `G_scout` (атомы по PXS-1 §1.4, T6)

Каждый атом — провабельный шаг с владельцем SCOUT и предикатом `Φ`. Рёбра — зависимости (PXS-1 §3).

```
 s0 sources ──▶ s1 extract ──▶ s2 detect_pain ──▶ s3 score ──▶ s4 rank ──▶ s5 emit_list
                                     ▲
                                     │ (param)
                              D.icp_signals  (из домена; готовит SCRIBE)
```

| атом | action ∈ Σ | вход (`pre`) | эффект (`eff`) |
|---|---|---|---|
| `s0` sources | `survey` | `D.sources[]` валиден | сырые записи из 2ГИС/Я.Карт/Instagram/Dikidi-каталога |
| `s1` extract | `extract` | `s0` PASS | нормализованные `targets[]` (имя, контакт, канал) |
| `s2` detect_pain | `detect_pain` | `s1` PASS ∧ `D.icp_signals` готов | у целей помечены сигналы боли + **доказательство** (скрин/ссылка) |
| `s3` score | `score` | `s2` PASS | каждой цели — числовой скор (ICP-фит × сила боли) |
| `s4` rank | `rank` | `s3` PASS | `targets[]` отсортирован по скору |
| `s5` emit_list | `emit_evidence` | `s4` PASS | `targets.json` + `SCOUT_LIST_PROOF.json` → открывает ребро на HERMES |

`s5` — это в точности атом `SCOUT.build_list` из трассы PXS-1 §8. Его PASS открывает `HERMES.touch`.

---

## 3. Предикаты `Φ` — что даёт PASS (реальные проверки, PXS-1 §1.3)

Каждый предикат — оператор из алфавита `{exists, proof_pass, json_true, json_eq, json_nonempty}`, читающий
реальный файл. **Нет «поверь».**

```
Φ(s1):  { json_nonempty: targets[]  }                       # извлечение что-то дало
Φ(s2):  { json_true: all_have_pain_evidence,                # КАЖДАЯ цель в списке имеет скрин/ссылку боли
          json_true: pain_from_icp_signals_only }           # боль — из D.icp_signals, не выдумана
Φ(s3):  { json_true: every_target_scored }                  # нет цели без скора
Φ(s4):  { json_true: sorted_desc_by_score }                 # порядок реальный
Φ(s5):  { json_nonempty: targets[],                         # список непуст
          json_true: each_target_has_evidence_ref,          # к каждой цели приложено доказательство
          json_true: legal_guard_passed }                   # §4 — легальность соблюдена
```

Ключевой инвариант честности: **цель без приложенного доказательства боли НЕ попадает в список.**
`emit_list` с пустым доказательством = FAIL по `Φ(s5)` ⇒ ребро на HERMES не открывается ⇒ HERMES не пишет
впустую. Так SCOUT не может «накидать имён» — он обязан показать боль на каждой.

## 4. Закон SCOUT `Λ_SCOUT` (легальность — твой «по шагам законно»)

Усиливает `Λ₀` (PXS-1 §5), не ослабляет. Эти проверки входят в `legal_guard_passed`:

- **L1 — публичность.** Собирается только то, что **публично опубликовано самой клиникой** (карточка 2ГИС,
  открытый профиль, открытый отзыв). Никаких закрытых данных, обходов авторизации, скрытых API.
- **L2 — лимиты и вежливость.** Частота опроса источника ограничена; уважается `robots`/ToS канала.
  Превышение лимита = FAIL атома `s0` (fail-closed), а не «тихо продолжил».
- **L3 — минимизация ПДн.** Хранится минимум для контакта и доказательства боли; никаких лишних
  персональных данных. Доказательство боли — про **бизнес-факт** (не ответили/нет записи), не про личность.
- **L4 — SCOUT не касается.** Грань ролей: SCOUT только *находит и доказывает*. Любое сообщение владельцу —
  это HERMES, под отдельным approve (PXS-1 §5: рассылка без approve запрещена `Λ₀`). Смешение = FAIL.

> Почему это снимает риск, а не добавляет: легальность проверяется как предикат `Φ(s5)`. Нелегально
> собранная цель **не пройдёт гейт** и не дойдёт до касания. Твоя репутация защищена конструкцией.

## 5. Рождение SCOUT — `Π(R_SCOUT, D)` (TFS-1 §2)

```
Π(R_SCOUT, D):
  bind   Σ → реальные опросники источников D.sources (коннекторы)
  mount  читает D.icp_signals, D.vocabulary (язык ниши)
  attach Λ_SCOUT ⊕ D.law_overrides
  init   f_SCOUT = 0, локальная память пуста, глобальный геном G_SCOUT подключён
  register entity_substrate/entities/<D.id>/scout/  + proof рождения → SOVEREIGN/PROOF
```

Живёт как сущность: `entity_substrate/entities/<domain>/scout/`, память в `SOVEREIGN/MEMORY`.
«Вечный» = состояние персистентно, возобновляемо по T4 PXS-1 (рестарт продолжает с фронтира своего под-DAG).

## 6. Что переиспользуем из уже построенного (не строим заново)

SCOUT не пишется с нуля — он опирается на твой существующий спайн знаний:

| нужда SCOUT | реальный готовый кирпич |
|---|---|
| `survey`/`extract` источников | `scripts/socc/scan_knowledge_sources_v1.py`, `ingest_knowledge_sources_v1.py` |
| поверхность знания о цели `K` | `socc_knowledge_spine_v1.py`, `socc_memory_spine_v2.py` |
| прогон атома через гейт | `socc_lawful_step_engine_v1.py :: run_step(spec)` (PXS-1 §2) |
| атомарный переход s_i→s_{i+1} | `socc_self_building_atomic_commit_enforcer_v1.py` |
| место proof | `SOVEREIGN/PROOF` |

Новое здесь — только **детектор боли** (`detect_pain` по `D.icp_signals`) и **скоринг**. Остальное —
обвязка существующих кирпичей в под-DAG `G_scout`. Это держит масштаб работы честным и малым.

## 7. Фитнес и эволюция (стыковка TFS-1 §6, PXS-1 §9)

```
f_SCOUT = precision = |целей, которых HERMES подтвердил как реальную боль| / |целей в списке|
```

LEDGER меряет: какие сигналы боли реально конвертили в ответы (обратная связь от HERMES). Сигнал, дающий
прирост `precision` ≥ θ на ≥ k доменах, промотируется `K_SCOUT → G_SCOUT` через гейт `φ_promote` (PXS-1 §9):
обезличенно, воспроизводимо, не нарушая `Λ`. Итог: **детектор боли умнеет на каждом домене** — стоматология
учит барбершоп, какие сигналы предсказывают деньги.

## 8. Тест приёмки SCOUT (фальсифицируемый)

SCOUT-SPEC-1 доказан ⟺:

```
(SC1 evidence-or-nothing) Подсунуть цель без доказательства боли → s5 = FAIL,
                          targets.json не выпущен, ребро на HERMES закрыто.        [Φ(s5)]
(SC2 legality)            Источник вне L1/L2 → s0/s5 = FAIL, цель не в списке.     [§4]
(SC3 domain-swap)         Подать D=barbershop (только домен-файл, 0 правок кода) →
                          SCOUT рождается и выдаёт список с болью барбершопов.     [TFS-1 F1]
(SC4 handoff)             s5 PASS ⟹ π(s5).next_after_pass == "HERMES.touch"
                          ⟹ HERMES.touch входит в Fr(G).                          [PXS-1 §8]
```

Пока тесты красные — SCOUT заявлен, но не доказан, и мы это честно видим. Зелёные — «под капотом ищет»
становится proof, и узел `SCOUT-движок` в атомарном мапе загорается.

---

## 9. Граница честности (что SCOUT НЕ делает)

- Не пишет владельцам и не «продаёт» — это HERMES под approve (L4).
- Не утверждает, что цель **купит** — только что у неё **видна** боль из `D.icp_signals` с доказательством.
- Не собирает закрытые/личные данные — только публичные бизнес-факты (§4).
- DAG-фронтир под-графа `G_scout` — DESIGN до прохождения §8; линейный движок под ним уже доказан (PXS-1 §12).

---

> **Место в карте.** SCOUT — первый кирпич вечной машины добычи: находит и **доказывает** боль, открывает
> дверь HERMES, кормит LEDGER. TFS-1 дал ему форму роли, PXS-1 — запер его работу реальностью, домен `D` —
> навёл на конкретную нишу. Один SCOUT, любой продукт.
