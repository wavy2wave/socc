## 0. Зачем FORGE и почему он — сердце «дублируется на любой продукт»

FORGE превращает «да» от владельца в **живую ANNA под его клинику за < 1 дня**. Но глубже: FORGE — это
**операционный исполнитель функции рождения `Π`** из TFS-1 §2. Когда FORGE штампует ANNA под клинику —
он буквально выполняет `Π(R_ANNA, D_clinic)`. Значит:

> Доказать FORGE = доказать функтор. Если FORGE штампует ANNA из домен-файла без правок кода — то по той же
> механике он штампует **любую роль на любой продукт** (барбершоп, вет, юр-приём). Один FORGE рождает всё.

Это камера №5 твоей доктрины: *фабрика должна штамповать до выстрела — залп, который не вытянешь по
онбордингу, = смерть репутации.* FORGE снимает страх **«не вытяну поток»**: поток штампует конвейер, не ты.

### 0.5 На пальцах (такт УЧУ — два термина)

> **Smoke-test** — проверка «дымом»: до того как ANNA коснётся живого пациента, она проходит фейковую бронь
> в тест-петле — диалог → запись → запись **появилась в реальном календаре клиники**. Зачем: go-live только
> после зелёного smoke. Никогда не выводим в бой непроверенное — это защита и пациента, и репутации.
>
> **Fail-closed рождение** — если домен-файл клиники неполный (нет цен, нет интеграции), FORGE **не рождает
> половину ANNA**, а честно останавливается. Зачем: полу-робот хуже, чем никакого — он сломается на пациенте.
> Лучше видимый STOP «не хватает X», чем кривой go-live.

## 1. FORGE как роль `R_FORGE` (шаблон TFS-1 §1.1)

| поле | значение |
|---|---|
| `id` | `FORGE` |
| `mandate` | штамповать живую ANNA под клинику за < 1 дня (исполнять `Π` на конвейере) |
| `responsibilities` | ingest данных клиники · сборка домен-файла · чеканка ANNA из substrate · подключение к системе записи · smoke-test · go-live |
| `Σ` | `ingest(clinic)` · `build_domain(D)` · `mint(Π(R_ANNA,D))` · `connect(D.integration)` · `smoke_test()` · `go_live()` |
| `Λ` | §4 — fail-closed рождение · нет go-live без smoke PASS · go-live требует доступов оператора · доменная изоляция |
| `f` | доля онбордингов **< 1 дня** со smoke-test PASS (TFS-1 §6) |
| `Φ` | §3 |
| `deps` | вход: `HERMES`(«да» клиники), домен-схема (TFS-1 §3), substrate · выход: `WARDEN`(живую ANNA под охрану), `LEDGER`(метрики онбординга) |

FORGE доменно-инвариантен в чистом виде: он не знает «стоматология» — он знает «возьми домен-файл, исполни
`Π`». Поэтому тот же FORGE штампует барбершоп (TFS-1 F1) — меняется только `D`.

## 2. Под-DAG FORGE `G_forge` (атомы, PXS-1 §1.4)

```
 f0 ingest ──▶ f1 validate_domain ──▶ f2 mint(Π) ──▶ f3 connect ──▶ f4 smoke_test ──▶ f5 GO-LIVE ──▶ WARDEN
                     │ (fail-closed)                                       │             ▲
                     └─ неполный D → STOP «не хватает X», рождения нет      │        оператор: доступы
                                                                    бронь в реальном календаре
```

| атом | action | вход (`pre`) | эффект | узел |
|---|---|---|---|---|
| `f0` ingest | `ingest` | «да» клиники (HERMES) | собраны цены, врачи, часы, политика | A3 |
| `f1` validate_domain | `build_domain` | `f0` PASS | домен-файл по схеме TFS-1 §3; все `[R]` на месте — иначе **STOP** | — |
| `f2` mint | `mint` | `f1` PASS | `Π(R_ANNA,D)`: per-clinic ANNA в `entity_substrate/.../anna` + proof рождения | A1 |
| `f3` connect | `connect` | `f2` PASS | коннектор к `D.integration` (Dikidi/1С/IDENT) живой | A2 |
| `f4` smoke_test | `smoke_test` | `f3` PASS | тест-бронь **появилась в реальном календаре** | A1·A2 proof |
| `f5` go_live | `go_live` | `f4` PASS ∧ доступы оператора | ANNA в бою, передана WARDEN | go-live |

Повтори `f0…f5` на 3 клиниках подряд за < 1 дня каждая → узел **A5 (фабрика)** зелёный = тест функтора пройден.

## 3. Предикаты `Φ` (реальные, PXS-1 §1.3)

```
Φ(f1):  { json_true: domain_complete }                  # все [R]-поля схемы §3 заполнены; иначе FAIL (fail-closed)
Φ(f2):  { proof_pass: birth_proof,                       # рождение оставило proof в SOVEREIGN/PROOF
          json_true: no_half_entity }                    # сущность целая или её нет (TFS-1 §2.5, I3)
Φ(f3):  { json_true: connector_handshake_ok }            # реальное соединение с системой записи
Φ(f4):  { json_true: test_booking_in_real_calendar }     # бронь ВИДНА в их календаре — не «вроде записал»
Φ(f5):  { json_true: smoke_passed,                        # без зелёного smoke go-live невозможен (FG2)
          json_true: operator_access_confirmed }          # доступы подтверждены человеком (FG3)
```

Инвариант честности: `f5` без `test_booking_in_real_calendar` = FAIL. FORGE не выводит «вроде работает» —
go-live открывается только реальной бронью в реальном календаре. Это узлы A1/A2 как proof, не как обещание.

## 4. Закон FORGE `Λ_FORGE`

Усиливает `Λ₀`:
- **FG1 — fail-closed рождение.** Неполный `D` → нет полу-ANNA, виден STOP с причиной (TFS-1 §2.5, I3).
- **FG2 — нет go-live без smoke PASS.** Непроверенная ANNA не касается живого пациента.
- **FG3 — go-live требует доступов оператора.** Человеческий атом: подпись/доступы ставишь ты.
- **FG4 — доменная изоляция (I2).** Данные клиники A не текут к клинике B; `K(Dₐ) ∩ K(D_b) = ∅` по сырым данным.

> Почему это снимает страх потока: конвейер штампует, но **каждый штамп заперт smoke-тестом и твоими
> доступами.** Скорость не ценой качества — скорость *потому что* каждый шаг провабелен и не надо проверять руками.

## 5. FORGE = операционный `Π` (стыковка TFS-1 §2)

```
f2.mint исполняет ровно Π(R_ANNA, D):
  bind   Σ_ANNA → D.integration/channels      (абстрактная операция → коннектор)
  mount  K(D) как память (история, цены, врачи клиники)
  attach Λ_ANNA ⊕ D.law_overrides             (не диагностирую ⊕ доменные законы)
  init   фитнес + память (локальный пуст, геном G_ANNA подключён)
  register entity + proof рождения → SOVEREIGN/PROOF
```

Поскольку `Π` принимает **любую** роль, тот же `f2` штампует не только ANNA, но и SCOUT/HERMES/… под новый
домен. FORGE — это конвейер рождения всего ростера. Вот где «вся команда дублируется» становится механикой.

## 6. Тест приёмки FORGE = тест функтора (фальсифицируемый, TFS-1 §8)

```
(FG-T1 fail-closed)  домен-файл без [R]-поля → f1 = FAIL, ANNA НЕ рождена наполовину.        [FG1/I3]
(FG-T2 real-booking) smoke без брони в реальном календаре → f4/f5 = FAIL, go-live закрыт.    [FG2/Φ(f4)]
(FG-T3 ФУНКТОР)      domain=barbershop (только домен-файл, 0 правок кода) → FORGE штампует
                     рабочую ANNA барбершопа, smoke PASS, время < 1 дня.                     [TFS-1 F1/§8]
(FG-T4 фабрика A5)   3 клиники подряд, каждая < 1 дня, smoke PASS → узел A5 🟢.
```

FG-T3 — это и есть момент, когда «дублируется на любой продукт» перестаёт быть словом. Пока красный — функтор
заявлен, не доказан, и мы честно это видим. Зелёный — у тебя в руках фабрика, переживающая залп.

## 7. Граница честности (что FORGE НЕ делает)
- Не ищет/не привлекает (SCOUT/HERMES) и не считает чек (LEDGER) — только **рождает и выводит** ANNA.
- Не выводит в бой без smoke PASS и без твоих доступов (FG2/FG3).
- Не рождает полу-сущность (FG1) — целая или STOP.
- DAG-исполнение `G_forge` и A5 — DESIGN до §6; гейт и `Π` под ним — формализованы (PXS-1 §2, TFS-1 §2).

> переданная WARDEN. Доказав FORGE на барбершопе без правок кода, ты доказываешь весь функтор TFS-1 —
> сердце масштаба «один подход, любой продукт».
