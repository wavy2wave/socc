## 0. Зачем MERCHANT и какой страх убивает

MERCHANT убивает страх **«найти-то нашли, а кто это реально сделает».** Он берёт доказанную связку и
проводит её через рынок до **исполненного обязательства**: разместил оффер → принял заказ → исполнил
(отгрузка/услуга). Дальше — LEDGER верифицирует деньги. MERCHANT — руки органа.

> Правило купца: **обязательство реально исполнено — иначе claim не заводится.** Доставленный товар клиенту
> в срок / оказанная услуга — вот что даёт право на ₽. Нажал «исполнено» без исполнения = нарушение.

## 1. MERCHANT как роль `R_MERCHANT` (шаблон TFS-1 §1.1)

| поле | значение |
|---|---|
| `id` | `MERCHANT` |
| `mandate` | провести доказанную связку через рынок до исполненного обязательства (оффер → заказ → отгрузка) |
| `responsibilities` | листинг оффера · ценообразование по `D.pricing` · приём заказа · исполнение/отгрузка · завод claim |
| `Σ` | `list_offer(item, D)` · `intake_order(D.integration)` · `fulfill(order)` · `claim(order → LEDGER)` |

| `f` | доля офферов, дошедших до заказа × доля заказов, исполненных в срок (конверсия и надёжность) |

| `deps` | вход: связка от `PROSPECTOR` · выход: claim в `LEDGER`(t2/t3) |

Доменно-инвариантен: канал листинга/приёма — из `D.integration` (Ozon FBS / лид-форма). Форма исполнения одна.

## 2. Под-DAG MERCHANT `G_merchant` (атомы — это t1..t3 связки MINT)

```
 t1 list ──▶ t2 order ──▶ t3 fulfill ──▶ (claim) ──▶ LEDGER.t4 verify_money
   │             │             │
   └─ w-gate ────┴─ w-gate ────┴─ w-gate   (WARDEN на каждом ребре)
```

| атом | action | вход (`pre`) | эффект |
|---|---|---|---|
| `t1` list | `list_offer` | связка PASS ∧ w-gate | оффер размещён; цена = `D.pricing_formula(item)` |
| `t2` order | `intake_order` | `t1` PASS ∧ реальный заказ | заказ из `D.integration` (Ozon FBS / лид); claim заведён (verified=false) |
| `t3` fulfill | `fulfill` | `t2` PASS ∧ обязательство исполнено | отгрузка/услуга отмечена; передаётся в LEDGER на верификацию |

## 3. Предикаты `Φ` (реальные)

```
Φ(t1):  { json_true: price_from_formula,            # цена из D.pricing, не вручную «на глаз»
          proof_pass: warden_gate }                  # красные линии/ToS пройдены
Φ(t2):  { json_true: order_from_real_integration,   # заказ из реального API/площадки
          json_true: claim_logged_unverified }       # claim в ledger verified=false
Φ(t3):  { json_true: obligation_actually_met,        # отгрузка/услуга реально произошла
          json_true: no_fulfill_without_event }       # «исполнено» без события = FAIL
```

Инвариант: отметка «исполнено» без реального события отгрузки/услуги = FAIL. Купец не врёт о доставке.

---

## 4. Закон MERCHANT `Λ_MERCHANT`
Усиливает `Λ₀`/`Λ_MINT`:
- **MR1 — обязательство реально.** `t3` PASS ⟺ товар отгружен/услуга оказана. Без события — нет claim.
- **MR2 — цена из формулы.** Цена оффера = `D.pricing_formula`. Произвол режется (прозрачность маржи).
- **MR3 — сущность создателя.** Листинг/приём только из легального кабинета создателя (наследует MN2).
- **MR4 — WARDEN на каждом шаге.** Любой атом проходит w-gate; нарушение RL → стоп, эскалация.

---

## 5. Фитнес и эволюция
- `f_MERCHANT` = конверсия оффер→заказ × надёжность заказ→исполнение-в-срок.
- Эволюция (PXS-1 §9): паттерн листинга/исполнения, поднявший конверсию/надёжность на ≥ k вселенных → промоушен.

---

## 6. Тест приёмки (фальсифицируемый)
```
(MR-T1 real-fulfill)  «исполнено» без события отгрузки → t3 = FAIL.                    [MR1]
(MR-T2 formula-price) цена не из D.pricing → t1 = FAIL.                                [MR2]
(MR-T3 real-order)    claim без реального заказа из integration → t2 = FAIL.           [Φ(t2)]
(MR-T4 warden)        нарушение RL на любом шаге → стоп + эскалация, claim не заводится. [MR4]
```

## 7. Граница честности (что MERCHANT НЕ делает)
- Не ищет связку (это PROSPECTOR) и не верифицирует деньги (это LEDGER) — он **исполняет**.
- Не отмечает «исполнено» без реального исполнения (MR1).
- Переиспользует `ozon-bridge/bridge.py` (приём заказов, bounded) и `parsers` (карточка/цена).

> **Место в карте.** MERCHANT — руки органа: превращает доказанную связку в исполненное обязательство,
> с которого LEDGER уже чеканит проверенную транзакцию. Без него связка — план; с ним — отгруженный товар.
