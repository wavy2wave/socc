# TFS-1 — Team Functor Specification

> Статус: **DESIGN / не запечатан в канон.** Печать в sovereign canon — за оператором, по закону SOCC.
> Версия: 1.0 · Слой: штабная инженерия (как рождается команда на любой продукт)
> Парный документ: [PXS-1 — Proof-Gated Execution](./PXS-1_proof_dag_execution.md)

---

## 0. Зачем этот документ

Один оператор. Под капотом — не пустота, а **команда сущностей**, которая рождается заново
под **любой** продукт (стоматология, барбершоп, юр-приём, автосервис) **одной операцией** и
начинает работать мощно, точно, без ошибок.

TFS-1 отвечает на вопрос *«ENTITY — рождение, а это что?»* строго: не метафорой, а **функтором**.

Ключевое свойство, которое доказывается ниже:

> **Геном команды (роли и их связи) — инвариант домена. Меняется только параметр-домен.**
> Поэтому «сделал для стоматологии → продублировал на барбершоп» — это не копипаст и не
> вторая стройка, а *применение той же функции к другому аргументу.* Улучшил роль один раз —
> улучшились ВСЕ продукты сразу.

---

## 1. Объекты

### 1.1 Роль (Role) — `Rᵢ`
Доменно-инвариантная спецификация одной функции команды. Формально кортеж:

```
Rᵢ = ⟨ id, mandate, responsibilities, Σᵢ, Λᵢ, fᵢ, Φᵢ, deps ⟩
```

| поле | смысл |
|---|---|
| `id` | SCOUT · HERMES · ANNA · FORGE · WARDEN · LEDGER · SCRIBE · CONDUCTOR |
| `mandate` | одно предложение: за что отвечает |
| `responsibilities` | множество обязанностей (что владеет) |
| `Σᵢ` | **грамматика действий** — конечный алфавит операций роли (что она вообще умеет делать) |
| `Λᵢ` | **закон роли** — инварианты, которые НЕЛЬЗЯ нарушать (напр. ANNA: «не диагностирую») |
| `fᵢ` | **фитнес-функция** — числовая мера «насколько хорошо роль справляется» (см. §6) |
| `Φᵢ` | предикаты-доказательства роли (передаются в [PXS-1](./PXS-1_proof_dag_execution.md)) |
| `deps` | от каких ролей зависит (ребро DAG команды) |

> `Σ` и `Λ` доменно-инвариантны по форме; их **привязки** (bindings) задаёт домен (§2).
> Пример: у HERMES операция `send(channel, msg)` ∈ Σ всегда; *какой* канал и *какой* закон
> анти-спама — приходит из домена.

### 1.2 Ростер (Roster) — `R`
Упорядоченное множество ролей с их зависимостями: `R = ⟨ {Rᵢ}, deps ⟩`. Это **геном команды.**
Ростер не зависит от продукта. Барбершоп и стоматология делят один ростер.

Базовый ростер SOCC (v1):

```
SCOUT  ──находит──▶ HERMES ──привлекает──▶ ANNA(demo) ──"да"──▶ FORGE ──go-live──▶ WARDEN
   │                   │                                            │                 │
   └───────────────────┴──────────── метрики ───────────────▶ LEDGER ◀───────────────┘
SCRIBE  : кует боеприпасы (позиционирование, ROI, тексты) для HERMES/ANNA
CONDUCTOR : гоняет всех по PXS-1 (= socc_lawful_step_engine, расширенный до DAG)
```

### 1.3 Домен (Domain) — `D`
**Параметр-пучок.** Всё, что отличает один продукт от другого, и НИЧЕГО больше:

```
D = ⟨ id, persona, vocabulary, sources[], integration,
       icp_signals[], channels[], pricing, law_overrides, surface ⟩
```

См. полную схему в §3. Домен — это единственное, что пишет человек, чтобы родить новую команду.

### 1.4 Поверхность знания (Knowledge surface) — `K(D)`
Срез памяти, построенный из `D.sources[]` существующим спайном
(`scripts/socc/socc_knowledge_spine_v1.py`, `socc_memory_spine_v2.py`).
`K(D)` — это «что команда знает про ЭТОТ бизнес». Изолирована по домену (§5).

### 1.5 Сущность (Entity) — `Eᵢ`
**Рождённая** роль: живой, персистентный экземпляр роли, привязанный к домену.
Живёт в `entity_substrate/entities/<domain.id>/<role.id>`. Память — в `SOVEREIGN/MEMORY`.
«Вечная и неубиваемая» — потому что состояние персистентно и возобновляемо (см. §7, и T4 в PXS-1).

## 2. Рождение — функция `Π`

> Это формальный ответ на «ENTITY — рождение, а это что?»

**Рождение сущности** — функция, связывающая роль с доменом:

```
Π : (Role, Domain) → Entity
Π(Rᵢ, D) = Eᵢ
```

Операционально `Π(Rᵢ, D)` выполняет ровно следующее (детерминированно, fail-closed):

1. **bind** грамматику `Σᵢ` к интеграциям домена `D.integration`, `D.channels`
   (абстрактная операция → конкретный коннектор).
2. **mount** поверхность знания `K(D)` как читаемую память роли.
3. **attach** закон `Λᵢ ⊕ D.law_overrides` (закон роли усилен доменными ограничениями).
4. **init** фитнес-состояние `fᵢ` и память (локальный tier пуст, глобальный геном `Gᵢ` подключён — §6).
5. **register** запись сущности в `entity_substrate` + эмит **proof рождения** в `SOVEREIGN/PROOF`.

Если любой шаг невозможен (нет коннектора, неполный домен) → `Π` **не рождает половину сущности**,
а возвращает HALT с причиной (fail-closed). Полусущностей не бывает — это инвариант.

## 3. Схема домена — чек-лист «новый продукт за день»

Чтобы родить команду на барбершоп, человек заполняет ОДИН файл по этой схеме.
`[R]` = required (без него рождения нет), `[O]` = optional (есть дефолт).

```yaml
domain:
  id:            barbershop_msk_01        # [R] уникальный id домена
  persona:                                 # [R] лицо ANNA для этого домена
    name: "Алиса"
    tone: "дружелюбно, на ты, коротко"
  vocabulary:    [фейд, тейпер, бородка…]  # [R] язык отрасли (для SCOUT/HERMES/ANNA)
  sources:                                 # [R] откуда строится K(D) (спайн их съест)
    - price_list.pdf
    - faq.md
    - booking_rules.md
  integration:                             # [R] куда ANNA пишет брони
    type: dikidi | yclients | 1c | custom
    creds_ref: vault://…                   # ссылка, не сам секрет
  icp_signals:                             # [R] что для SCOUT = «боль» в этой нише
    - no_online_booking
    - slow_dm_reply
    - reviews_mention "не дозвониться"
  channels:      [telegram, instagram_dm]  # [R] где HERMES касается
  pricing:                                 # [R] модель ценности для ROI (SCRIBE/LEDGER)
    metric: "пропущенная заявка"
    avg_ticket: 1500
  law_overrides:                           # [O] доп. законы поверх Λ ролей
    - no_medical_claims
  surface:       {…}                        # [O] UI/брендинг demo-бота
```

Отсутствие хоть одного `[R]` → команда **не рождается** (честно, видимо), а не рождается криво.

## 4. Функтор `Team`

Команда домена — это все роли ростера, рождённые в `D` и связанные по DAG зависимостей:

```
Team(D) = ⟨ { Π(Rᵢ, D) : Rᵢ ∈ R }, deps ⟩
```

`Team` — **функтор** из категории доменов **Dom** в категорию команд **Teams**:
он переносит не только объекты (домен → команда), но и **структуру** (связи ролей).

### Законы функтора (почему дублирование математически надёжно)

- **(F1) Сохранение структуры.** Для любого `D` граф зависимостей `Team(D)` ≅ `deps` ростера.
  Проводка ролей инвариантна: меняются `K`, привязки `Σ`, параметры `Λ` — **не топология.**
  *Следствие:* команда на барбершоп связана так же, как на стоматологию. Перенос — не пересборка.

- **(F2) Композиция / подъём улучшений.** Добавил/улучшил роль в ростере `R → R'` →
  изменение **поднимается во ВСЕ** `Team(D)` при следующем рождении.
  *Следствие — это и есть «улучшил один раз, выиграли все продукты».* HERMES научился новому
  крючку в стоматологии → крючок доступен барбершопу (через глобальный геном, §6).

## 5. Инварианты и гарантии

- **(I1) Детерминизм.** Один `(R, D)` → одна `Team(D)` с точностью до накопленного состояния обучения.
  Рождение воспроизводимо.
- **(I2) Доменная изоляция (приватность).** Для разных доменов `K(Dₐ) ∩ K(D_b) = ∅` по **сырым данным.**
  Делится **только геном ролей** (паттерны), не данные клиентов. Усиливается `Λ`. Это контракт приватности
  между клиниками/барбершопами — данные одного клиента физически не текут к другому.
- **(I3) Fail-closed рождение.** Неполный `D` никогда не даёт полукоманду (§2.5, §3).
- **(I4) Прозрачность.** Каждое рождение оставляет proof в `SOVEREIGN/PROOF`; невидимых сущностей нет.

## 6. Двухуровневая память = механизм эволюции

> «Всё живое стремится к эволюции» — здесь это не лозунг, а структура.

Каждая роль имеет ДВА уровня памяти:

```
Kᵢ(D)  — локальный  : приватные данные/опыт ЭТОГО домена         (изолирован, I2)
Gᵢ     — глобальный : геном роли, паттерны across ВСЕХ доменов   (общий, обезличенный)
```

**Цикл эволюции (per role):**

1. Сущность действует, фитнес `fᵢ` измеряет результат (см. метрики ниже) — это делает LEDGER, реально.
2. Паттерн, давший прирост `fᵢ` выше порога `θ` на ≥ k доменах, **промотируется** `Kᵢ → Gᵢ`
   через гейт (PXS-1 φ: «прирост воспроизводим, обезличен, не нарушает Λ»).
3. Новые рождения `Π(Rᵢ, ·)` стартуют уже с обновлённым `Gᵢ`.

Это **эволюционный контур с отбором по фитнесу**: выживают паттерны, реально поднимающие число.
Конкурентов система обгоняет не разово, а **монотонно** — каждый домен кормит общий геном.

Примеры фитнес-функций (числовые, реальные, считает LEDGER):

| роль | fᵢ (что максимизируем) |
|---|---|
| SCOUT | precision списка = (целей с подтверждённой болью) / (всего в списке) |
| HERMES | reply-rate · demo-rate на касание; штраф за жалобы/спам |
| ANNA | доля диалогов, дошедших до брони, без нарушений Λ |
| FORGE | доля онбордингов < 1 дня со smoke-test PASS |
| WARDEN | uptime · (нарушений Λ = 0); иначе fᵢ → 0 (закон важнее) |
| LEDGER | точность прогноза ₽-возврата vs факт |

## 7. Почему «вечная и неубиваемая»

- Состояние каждой `Eᵢ` персистентно: `entity_substrate/entities/<D>/<R>` + `SOVEREIGN/MEMORY`.
- Прогресс работы возобновляем: см. **T4 (Resumability)** в PXS-1 — рестарт продолжает с фронтира,
  атомы идемпотентны, двойного эффекта нет.
- Геном `Gᵢ` переживает любой отдельный домен: закрыл барбершоп — паттерны остались в `Gᵢ`.

Команда не увольняется, не забывает, не устаёт, **аккумулирует**. Это её родовое качество, не надстройка.

## 8. Тест приёмки функтора (фальсифицируемый)

Заявление TFS-1 истинно ⟺ выполняется:

```
∃ файл domain=barbershop (по схеме §3), такой что:
   Team(barbershop) рождает все роли ростера,
   smoke-test каждой сущности = PASS,
   при НУЛЕ изменений в коде ролей/ростера.
   Время от «есть domain-файл» до «команда жива» < 1 дня.
```

Этот тест = узел `A5` (фабрика) tech-tree. Пока он красный — функтор не доказан, и мы это честно видим.
Когда зелёный — «дублируется на любой продукт» перестаёт быть обещанием и становится proof.

---

## 9. Связь с PXS-1

TFS-1 говорит, **что рождается** (команда). [PXS-1](./PXS-1_proof_dag_execution.md) говорит,
**как её работа честно движется**: каждая сущность владеет под-DAG задач; передача
«SCOUT done → HERMES start» — это ребро DAG, открываемое только реальным proof.
Вместе = фабрика команд, каждое действие которых заперто реальностью.
